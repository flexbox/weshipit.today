### 🟧 EXPO Chunk 1 — Upgrade the app foundation to Expo SDK 58

**Goal:** Move the app onto the Expo SDK 58 and React Native 0.88 baseline so it is ready for current iOS 27 tooling while keeping the existing user flows stable. Source: [Expo SDK 58](https://expo.dev/changelog/sdk-58).

**Scope:**
- Record the current Expo, React Native, and native-module versions before changing dependencies.
- Upgrade the Expo package and compatible Expo modules using the repository’s package manager; apply only required config-plugin or native-project changes.
- Run Expo dependency diagnostics and resolve upgrade-related warnings that block a build.
- Produce one internal iOS build and one internal Android build, then smoke-test launch, navigation, authentication, and the most-used data screen.

**Out of scope:** iPhone Duo-specific layouts, a full redesign, unrelated dependency upgrades, and production store submission.

**Dependencies:** A clean working branch, the project’s existing Expo/EAS project, and access to an iOS and Android build environment.

**Acceptance criteria:**
- `package.json` and lockfile resolve Expo SDK 58 with React Native 0.88-compatible packages.
- Expo diagnostics complete without unresolved version or config-plugin errors.
- Internal iOS and Android builds install and launch on a real or hosted device.
- The smoke-tested flows work without new crash, navigation, or authentication regressions.

**Estimated effort:** M

### 🟧 EXPO Chunk 2 — Configure a safe EAS OTA canary and rollback

**Goal:** Give the team a repeatable way to ship JavaScript, styling, and asset fixes quickly while preventing incompatible native changes from reaching users. Source: [TeamReach OTA cutover](https://expo.dev/blog/teamreach-ota-updates-relaunch).

**Scope:**
- Define stable and canary EAS Update channels or branches using the project’s existing runtime-version strategy.
- Add package scripts or documented commands for publishing a canary update and promoting a verified update.
- Publish a harmless canary change to an internal build and verify that the update is received.
- Exercise a rollback or republish procedure and document the operator checklist.

**Out of scope:** native-module changes, database migrations, a production cutover, and replacing the app’s release provider.

**Dependencies:** An existing EAS project, compatible runtime-version configuration, and an internal build that can receive EAS Updates.

**Acceptance criteria:**
- A canary update reaches only the intended internal channel.
- The internal build reports the expected update identifier after restart.
- A rollback or republish returns the test build to the previous known-good JavaScript bundle.
- The repository contains a short, copy/pasteable release and rollback procedure.
- The procedure explicitly rejects native changes as OTA-only releases.

**Estimated effort:** S

### 🟦 RN Chunk 3 — Pilot React Native Skia 3 Graphite rendering

**Goal:** Validate whether React Native Skia 3’s Graphite backend improves a representative animation or canvas screen without risking the rest of the app. Source: [The Great Graphite Migration](https://www.thereactnativerewind.com/issues/the-great-graphite-migration-derek-joins-fat-fighters-and-a-leaderboard-for-your-dependency-tree).

**Scope:**
- Add the Skia 3 package and required native configuration in an isolated, feature-flagged screen.
- Recreate one existing high-value visual—such as a chart, animated illustration, or image effect—in a small pilot component.
- Capture a simple before/after baseline for frame smoothness, load time, and memory on one iOS and one Android device.
- Record compatibility findings and keep the pilot disabled by default unless the baseline is met.

**Out of scope:** migrating every canvas, adopting three.js/WebGPU, broad animation refactors, and claiming a production-wide performance improvement from one screen.

**Dependencies:** Native build access, one existing visual use case suitable for isolation, and a test device or simulator for each target platform.

**Acceptance criteria:**
- The pilot screen builds on iOS and Android without affecting existing screens.
- The feature flag keeps the pilot disabled by default.
- A stakeholder can open the pilot screen and see the recreated visual.
- Before/after measurements and device details are recorded.
- The recommendation to continue, revise, or remove the pilot is documented.

**Estimated effort:** M

### ⚛️ REACT Chunk 4 — Verify shared components on React Native Web

**Goal:** Catch platform-specific regressions in the shared component layer before React Native Web and React 0.88-related changes reach users. Source: [This Week In React #301](https://thisweekinreact.com/newsletter/301).

**Scope:**
- Identify one high-traffic route and the shared components it renders.
- Run the route on the project’s existing web target, or add only the minimal command/configuration needed if web support already exists but is undocumented.
- Fix one clearly reproducible parity issue found in the route, with a focused regression test where practical.
- Add a short manual smoke checklist for mobile and web behavior.

**Out of scope:** a web redesign, SSR, SEO work, a new design system, and converting mobile-only features to web.

**Dependencies:** An existing React Native Web or Expo web target, a representative route, and access to the project’s normal web test command.

**Acceptance criteria:**
- The selected route loads in the web target without a console-blocking error.
- Primary navigation, buttons, text inputs, and loading/error states are usable with a pointer and keyboard.
- At least one identified parity issue is fixed or explicitly documented as a follow-up.
- The smoke checklist can be run by a non-technical stakeholder.

**Estimated effort:** S

### 🟦 RN Chunk 5 — Prepare the iOS 27 App Store creative asset pack

**Goal:** Make the app’s store listing ready for iOS 27’s new creative placements and updated screenshot requirements so the team can test acquisition messaging without waiting for a new binary. Source: [New App Store Creative Assets: Examples & Brief](https://neoads.substack.com/p/app-store-creative-assets).

**Scope:**
- Export one product-page header and one search-results asset using the app’s current brand system.
- Re-export the required iPhone screenshot at 1206 × 2622 and verify the image remains legible at store scale.
- Prepare a small asset manifest with filename, placement, target OS, dimensions, and message hypothesis.
- Upload the assets as a draft in App Store Connect or hand the prepared pack to the release owner for upload.

**Out of scope:** a full visual rebrand, paid acquisition, a statistically conclusive PPO experiment, video production, and iPhone Duo-specific screenshots.

**Dependencies:** Approved brand artwork, current app screenshots, and App Store Connect access or a named release owner.

**Acceptance criteria:**
- The header, search-results asset, and updated screenshot are exported in the required formats and dimensions.
- A non-technical stakeholder can identify which asset appears in each placement.
- The asset manifest records the message hypothesis and review status.
- Assets are visible in an App Store Connect draft or delivered as a complete upload-ready package.
